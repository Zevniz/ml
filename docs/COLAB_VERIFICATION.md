# Проверка воспроизводимости в Google Colab (20.08.2026)

## Зачем этот документ

Правила этапа требуют, чтобы решение запускалось в Google Colab **без ручных правок**, а
инференс воспроизводил в точности отгруженное предсказание. Нарушение любого из условий —
**0 очков за весь этап**, что перевешивает любую возможную борьбу за F1
(см. `docs/KNOWN_LIMITATIONS.md` и оценку в README). До 20.08.2026 фактический запуск в
Colab был единственным непроверенным звеном этого гейта: сверялись хэш файла, наличие
`train.csv`/`test.csv` в репозитории и доступность репозитория для клонирования, но не сам
прогон.

## Как проверялось

Через [`colab-mcp`](https://github.com/googlecolab/colab-mcp) (Google, Apache-2.0) — MCP-прокси
к сессии Colab в браузере. Ячейки взяты **побайтово из `main`**: скачанный
`raw.githubusercontent.com/Zevniz/ml/main/solution.ipynb` имеет
sha256 `9d20ea40c29dadcacbabab8914f239bd3a3105031a4b887ba24b266a0fdd2b6d`, совпадающий с
локальным файлом. Ячейки залиты в пустой ноутбук в исходном порядке и выполнены сверху вниз,
как это сделал бы проверяющий. Runtime: Colab CPU, Python 3.12.

## Найденный дефект: ноутбук падал при «Run all»

| ячейка | что делает | итог |
|---|---|---|
| 1 | `pip install` закреплённых версий | ✅ прошла |
| 2 | клонирует `Zevniz/ml`, `chdir` в клон | ✅ `/content/vk16` |
| 3 | `import solution; solution.main()` | ❌ `ImportError: cannot import name '_center' from 'numpy._core.umath'` |

Проверяющий, открывший ноутбук и нажавший Runtime → Run all, получал падение на третьей
ячейке.

**Причина.** Ячейка 1 переустанавливает `numpy` на закреплённую версию `2.2.1`, но ядро
Colab импортирует `numpy` ещё при старте, до первой ячейки. Дальше в одном процессе
смешиваются уже загруженный модуль и новые файлы на диске, и цепочка импорта
`scikit-learn` рвётся. Это стандартная ситуация «restart runtime after changing numpy»;
Colab обычно показывает кнопку RESTART RUNTIME, но только когда установка сделана
магией `!pip`/`%pip`, а не через `subprocess.check_call`, как здесь. То есть подсказки
проверяющий не видел.

**Это не дефект пинов и не дефект `solution.py`.** Замерено в том же Colab после установки:

```
numpy 2.2.1   pandas 2.2.3   scikit-learn 1.6.0
scipy 1.14.1  lightgbm 4.7.0 catboost 1.2.10   joblib 1.5.3
```

то есть все версии встали ровно как в `requirements.txt`, единственная копия `numpy` на
`sys.path`, и в **свежем интерпретаторе** внутри той же машины
`python -c "import sklearn"` завершается с кодом 0. Ломается исключительно то ядро,
которое само выполнило подмену.

## Правка

Изменена **одна** ячейка — третья. Вместо импорта в ядро ноутбука пайплайн запускается
дочерним процессом, который подхватывает закреплённые сборки чисто:

```python
process = subprocess.Popen(
    [sys.executable, "solution.py"],
    stdout=subprocess.PIPE, stderr=subprocess.STDOUT, text=True, bufsize=1,
)
for line in process.stdout:
    print(line, end="")
if process.wait() != 0:
    raise RuntimeError(f"solution.py exited with code {process.returncode}")
```

Вывод читается построчно, поэтому лог обучения по-прежнему виден в ячейке, а ненулевой код
возврата останавливает Run all. `solution.py`, признаки, модели, бленд и правило отсечения
**не тронуты**: `solution.py` уже имеет `if __name__ == "__main__": main()`, вызывающий тот
же `main()`. Ячейки 1, 2 и 4 оставлены без изменений — ячейка 4 проверена в том же
отравленном ядре и работает (её `import pandas` не задевает сломанную цепочку `sklearn`).

(`docs/HYPOTHESES_ROUND6.md`). То есть детерминизм даёт именно закреплённое окружение, и
поэтому любой будущий кандидат на загрузку должен собираться в среде из
`requirements.txt`, а не в произвольной локальной.

## Сохранённые в ноутбуке выводы

Все выводы ячеек в `solution.ipynb` заменены на выводы этого прогона в Colab, чтобы не
смешивать в одном файле два разных окружения. Раньше там лежал вывод прогона на Python
3.10, и по нему как раз и удалось установить, что записанный прогон делался не в Colab.

Ячейка 1 при этом не имеет вывода, и это ожидаемо: она ставит зависимости через
`subprocess.check_call`, который пишет в файловый дескриптор ядра, а не в
`sys.stdout` ячейки, поэтому лог `pip` уходит в журнал сервера Colab. Установка при этом
происходит — проверено списком версий выше. Если нужно, чтобы проверяющий видел
подтверждение установки прямо в ячейке, ячейку 1 можно перевести на то же построчное
чтение `Popen`, что и ячейку 3; на воспроизводимость это не влияет и здесь сознательно
не сделано, чтобы правка гейта оставалась минимальной — одна ячейка.

## Межплатформенный детерминизм: где он есть и где его нет

Отдельно замерено на macOS-arm64 в окружении, собранном **строго по `requirements.txt`**
(CPython 3.12.14, `uv venv`; версии совпадают с Colab до патча). Чистый клон, `rc=0`,
3.5 минуты против 16 в Colab:

| компонента | записано / Colab | macOS-arm64 с пинами | |
|---|---:|---:|---|
| `cat_all` | 362 | **400** | ✗ |
| `cat_recent` | 382 | **340** | ✗ |
| `lgb_neutral` | 432 | 432 | ✓ |
| `lgb_diverse` | 1483 | 1483 | ✓ |

То есть **LightGBM воспроизводится побитово между Linux-x86_64 и macOS-arm64, CatBoost —
нет**. Обе CatBoost-компоненты уехали в противоположные стороны (+38 и −42 итерации), что
указывает на порядок суммирования float при построении гистограмм, а не на несовпадение
версий: версии идентичны. Итоговый файл при этом расходится мало — совпадает 7420 строк из
7446, пересечение top-`k` 1769 из 1782 (расхождение 13 строк, Jaccard 0.9855), sha256
`52a9b78e…` вместо `bd1fb0bb…`.

Практические следствия, оба существенные:

- **Гейта это не касается**: гейт проверяется в Colab, а там воспроизведение байт-в-байт
  подтверждено трижды. Различие характеризовано и не блокирует сдачу.
- **Любой будущий кандидат на загрузку обязан собираться в Colab**, а не локально —
  локальная сборка даст другой файл даже при полностью корректных пинах. Локальное окружение
  при этом остаётся законной средой для *сравнения* вариантов внутри одного прогона (там
  baseline и эксперимент делят окружение) и быстрее в 4.5 раза.
