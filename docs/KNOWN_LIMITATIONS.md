# Известные ограничения и дефекты решения

Аудит кода от 2026-08-20. Все утверждения ниже проверены на артефактах и сохранённых
моделях, а не выведены из чтения кода. Раздел существует намеренно: дефекты, которые
видно ревьюеру, лучше объяснить вместе с ценой их исправления, чем оставить без
комментария.

## 1. Мёртвые признаки `owner_seen_before` / `content_seen_before`

`solution.py:363–366`:

```python
base_train["owner_seen_before"] = 1
base_val["owner_seen_before"] = raw_val["id_content_owner"].isin(set(raw_train["id_content_owner"])).astype(int)
base_train["content_seen_before"] = 1
base_val["content_seen_before"] = raw_val["id_content"].isin(set(raw_train["id_content"])).astype(int)
```

На обучении оба признака — константа `1` (по построению: любая строка train лежит в
train), а на валидации и тесте принимают `0/1`. Это **train/serve skew**: распределение
признака на инференсе отличается от того, что модель видела при обучении.

Практический вклад — доказуемо нулевой:

| Компонента | Состояние признаков |
|---|---|
| `cat_all_s42.cbm` | признаки **отсутствуют** в модели (86 признаков вместо 88) — CatBoost отбрасывает константу |
| `cat_recent_s42.cbm` | признаки **отсутствуют** (86 признаков) |
| `lgb_neutral_s42.pkl` | присутствуют, `feature_importances_` ровно `0` |
| `lgb_diverse_s42.pkl` | присутствуют, `feature_importances_` ровно `0` |

Дерево не может расщепить константу, поэтому ни одного сплита по этим признакам не
построено. Скошенность распределения на инференсе безвредна именно потому, что признаки
не используются.

Дополнительно они **избыточны**: `owner_seen_before` полностью дублирует
`id_content_owner_history_count > 0`, поскольку `oof_target_encode` (`solution.py:334`)
присваивает незнакомым сущностям `history_count = 0`.

**Почему не удалены.** У LightGBM `colsample_bytree = 0.85`, то есть колонки на каждое
дерево выбираются случайно. Удаление двух колонок из 97 меняет саму выборку колонок,
следовательно меняет деревья и итоговый ранжир — это ломает байт-точное воспроизведение
отгруженного файла с F1 `0.489` и стоит попытки загрузки при нулевом ожидаемом выигрыше
по метрике. Для CatBoost удаление вообще не изменит ничего (признаки уже отброшены).
Правку следует внести при любом следующем полном перепрогоне, а не отдельно.

## 2. Перемешанный `KFold` в target encoding на упорядоченных по времени данных

`solution.py:268` и `solution.py:317` используют `KFold(n_splits=5, shuffle=True)`.

Что это **не** является: утечкой в валидацию. Схема остаётся out-of-fold — ни одна
строка не видит собственную метку, — а валидация и тест получают маппинг, посчитанный
только по префиксу обучения (`solution.py:329` `mapping_full`, `solution.py:345`
`apply_te_to_new_data`). Поэтому оценки временного CV по этому пункту не завышены.

Что это является: мягким заглядыванием вперёд **внутри** обучения. Из-за перемешивания
target encoding строки может опираться на хронологически более поздние строки train.
Строгий вариант — KFold по времени, где фолд для кодирования состоит только из прошлого.
Признак при обучении получается чуть информативнее, чем на инференсе.

## 3. `models/` содержит только seed 42

`solution.py:540–546`:

```python
def _prune_models_if_needed(model_dir: Path) -> None:
    total_bytes = sum(path.stat().st_size for path in model_dir.iterdir() if path.is_file())
    if total_bytes <= MODEL_SIZE_LIMIT_BYTES:
        return
    for path in model_dir.iterdir():
        if path.is_file() and "_s42." not in path.name:
            path.unlink()
```

При превышении 15 MiB удаляется всё, что не содержит `_s42.`, поэтому сохранённый набор
моделей **недостаточен** для сборки бленда по seed-ам `42, 2026, 777`.

На гейт воспроизводимости это не влияет: `solution.py` обучает все seed-ы с нуля, а
сохранённая модель по условиям задачи опциональна. Пункт зафиксирован, чтобы ревьюер не
принял содержимое `models/` за полный набор артефактов финального бленда.
